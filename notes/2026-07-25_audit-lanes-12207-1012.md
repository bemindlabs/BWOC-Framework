# 2026-07-25 — Two new audit lanes: ISO/IEC/IEEE 12207 + IEEE 1012

Extends the `audit` kind with two standards lanes on the shared attestation
runtime, and — with IEEE 1012 — proves the kind is genuinely body-agnostic
(ISO, ISO/IEC, ISO/IEC/IEEE, *and* standalone IEEE).

## What changed

- `modules/plugins/audit-iso-iec-ieee-12207/` — software life-cycle processes
  (ISO/IEC/IEEE 12207:2017). 9 criteria across the process groups: agreement,
  project planning, assessment & control, configuration management, requirements
  definition, architecture/design, implementation/integration, verification &
  validation, maintenance. manifest + criteria.toml + audit.sh (cloned, name-
  substituted) + SPEC.md/th.
- `modules/plugins/audit-ieee-1012/` — verification & validation (IEEE 1012:2016).
  8 criteria: integrity levels, V&V planning (SVVP), independence, and
  requirements/design/implementation/test V&V + anomaly reporting. Same file set.
- `crates/bwoc-cli/tests/audit_iso_iec_ieee_12207.rs` + `audit_ieee_1012.rs` — 2
  e2e each (attest-2 → exit = fail-count; empty → exit = criteria-count).
- `docs/{en,th}/PLUGINS` audit-kind enumeration updated to list both new lanes
  and add the "standalone IEEE" publication shape.

## Decisions

- **12207 pairs with 29148, 1012 is its verification counterpart.** 29148 asks
  "are the requirements right?", 12207 "is the life cycle governed?", 1012 "is it
  verified & validated?" — a coherent systems/software-assurance trio, all on the
  attestation runtime.
- **IEEE 1012 named `audit-ieee-1012`, not `audit-iso-iec-ieee-1012`.** It is an
  IEEE-standalone standard (IEEE publishes it alone), so the name reflects the
  real publication body. This is the first non-ISO-prefixed audit lane and the
  point of the addition: the runtime audits by *criteria*, indifferent to how many
  bodies co-publish. The `Why` sections say so explicitly.
- **Reused the shared attestation runtime verbatim** (sed name-substitution of the
  29148 `audit.sh`). No new runtime code — the lanes are pure data (criteria.toml)
  + the standard's clause mapping. Deeper checks (parsing an actual project plan /
  SVVP / traceability matrix, not just an attestation) stay L1-deferred, matching
  every other lane's roadmap.
